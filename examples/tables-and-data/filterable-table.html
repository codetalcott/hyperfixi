The Code

<div _="on input or change add @hidden to <tbody tr/> in #products then remove @hidden from <tbody tr/> in #products where (its textContent.toLowerCase() contains #search's value.toLowerCase() and (#stock-only's checked is false or its @data-stock as Number > 0))"> <input id="search" type="search"> <label><input id="stock-only" type="checkbox"> In stock only</label> </div>

How it works:

  • <tbody tr/> in #products — a live element collection: the actual <tr> nodes, not copies.
  • where its … contains … — the predicate runs once per row with it bound to that row. Write its @data-stock, never a bare @data-stock (a bare @attr reads the handler's own element).
  • as Number — attribute values are strings; compare numerically on purpose.
  • add/remove @hidden — the platform's hidden attribute. Rows never leave the DOM, assistive tech sees the same state, and the server could just as well have rendered <tr hidden> itself — filtering is symmetric between server and client.
  • Two passes instead of negation: hide all rows, then unhide the ones matching every active filter.
  • Parenthesize compound predicates: where (A and B). Without the parentheses, X where A and B parses as (X where A) and B — a boolean, not a filtered collection.

Why @hidden and not show / hide?

show/hide write inline style.display — fine for ephemeral visual toggling. Filtering is state the server should be able to render, so it belongs in markup: the hidden attribute round-trips through HTML, CSS ([hidden]), and the accessibility tree.
