Sortable Table

Reorder server-rendered rows in place — nothing is serialized
Clicking a header moves the actual <tr> nodes into sorted order. No client row model, no templates, no re-render: type in a quantity box, sort, and the value (and your focus) survives, because the nodes move.

The Code

<th data-dir="asc" _="on click remove @aria-sort from <th/> in #products if my @data-dir is 'asc' set my @data-dir to 'desc' set @aria-sort to 'descending' on me start view transition put <tr/> in #product-rows sorted by its @data-price as Number desc at end of #product-rows end else …ascending variant… end">Price</th>

How it works:

  • <tr/> in #product-rows sorted by its @data-price as Number — sorts the live row elements by an attribute key. as Number matters: attribute reads are strings, and "100" sorts before "9" lexically.
  • put … at end of #product-rows — appending an existing child moves it, so putting the full sorted set back is an in-place reorder. Focus and input values survive; nothing is serialized or re-rendered.
  • start view transition … end — wraps the reorder so rows animate to their new positions in browsers with the View Transitions API (each row carries a unique view-transition-name). Elsewhere it just reorders instantly.
  • aria-sort — the handler maintains the real accessibility attribute, and the CSS direction arrows key off it (th[aria-sort="descending"]::after) — one source of truth for state, semantics, and style.

The hypermedia stance

The server rendered these rows once; the client only rearranges what already exists. The same markup conventions (stable row ids, data-* value mirrors) are exactly what lets a server round-trip (fetch … then morph) reconcile rows without losing state — client sort and server sort are two rungs of one ladder.
